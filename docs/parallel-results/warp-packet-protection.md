# Warp packet protection with linear nonce tickets

Wave-four lane 5 (design §35.1 item 2; RFC 9001). Base: `origin/main` at
`a5fa024b8d6f62eaa336337d825a2be2ec8972b4`. Branch:
`claude/project-thread-m56ni7` (the session's assigned branch; the prompt's
suggested name was `wave4/warp-packet-protection`). Tracking issue #41.

Changed paths: new `crates/vesper-warp-crypto/**`, this report, and the root
registration patch (separate commit). No other lane's paths, no CI, no CLI
wiring. The crate has no internal Vesper dependencies, as the wave-four
contracts require.

This is the Warp-specific packet-protection slice. It is **not** Vesper Vault
(§23) and does not claim to implement it; only the `NonceTicket` discipline
that Warp's send path needs is here.

## Public API

- `Cipher {Aes128Gcm, Aes256Gcm, ChaCha20Poly1305}` with `key_len`,
  `secret_len`, `confidentiality_limit` (2^23 for AES-GCM, 2^62 for
  ChaCha20-Poly1305) and `integrity_limit` (2^52 / 2^36), from RFC 9001 §6.6.
- `CryptoError`: one typed variant per rejection (secret length, cipher
  mismatch, CID too long, buffer too short, payload too large, pn offset,
  sample bounds, header form, pn out of range / reused / regression /
  mismatch / exhausted, confidentiality and integrity limits, stale ticket,
  key-phase mismatch, authentication failure, key update not permitted,
  key retired, pn reconstruction).
- `schedule`: `INITIAL_SALT_V1`, `Side`, `TrafficSecret` (`new`, `as_bytes`,
  `next_phase` = "quic ku", `key_material`, `keys`), `KeyMaterial` (`key`,
  `iv`, `hp`, `keys`), `DirectionalKeys {packet, header}`, `InitialSecrets`
  (`new_v1`, `initial_secret_v1`, `keys_for(side)`).
- `protect`: `PacketKey` (`nonce(pn)`), `HeaderKey` (`mask`, `apply`,
  `remove`), `Unprotected` (`pn_offset`, `pn_len`, `truncated_pn`,
  `first_byte`, `header_len`, `key_phase`, `encodes`, `reapply`).
- `ticket`: `NonceTicket`, `SealError {ticket, error}`, `TicketAudit`,
  `Sealer` (`new`, `with_confidentiality_limit`, `ticket`, `next_ticket`,
  `seal`, `abandon`, `audit`, ...), `Opener` (`new`, `with_integrity_limit`,
  `remove_header_protection`, `open`, `open_packet`, ...), `Opened`,

- `update`: `OneRttKeys` (`new(local, remote, retire_window_ns)`, `ticket`,
  `next_ticket`, `seal`, `abandon`, `on_packet_acked`,
  `key_update_permitted`, `initiate_key_update`, `open_packet`,
  `discard_expired`, generation/phase accessors), `OneRttOpened`.
- `retry`: `retry_integrity_tag`, `verify_retry_integrity` (QUIC v1).

## Packet-core boundary (lane 1)

Exactly the contract's byte-offset boundary; no dependency on `vesper-warp`.

Receive: lane 1 parses the header and gives `pn_offset`;
`HeaderKey::remove` / `Opener::remove_header_protection` removes header
protection in place and returns `Unprotected` (pn length 1–4, truncated
value, unprotected first byte); lane 1 reconstructs the full packet number;
`Opener::open(buf, &unprotected, full_pn)` opens with the **full** packet
number, since the RFC 9001 §5.3 nonce is built from it. `open` also checks
that the full number encodes the truncated one. `open_packet` and
`OneRttKeys::open_packet` run the same steps with a caller-supplied
reconstruction closure and re-apply header protection on any failure, so the
caller's buffer is byte-identical to its input. `buf` must be exactly one
packet; lane 1 splits coalesced packets by their Length field.

Send: lane 1 writes the unprotected header (truncated pn at `pn_offset`,
its length in the first byte's low two bits, and for 1-RTT the current
key-phase bit) and the plaintext into one buffer with 16 spare bytes, then
calls `seal(ticket, buf, pn_offset, payload_len)`, which returns the packet
length.

## Nonce tickets

`Sealer` is per key and per direction. `ticket(pn)` issues a ticket only for
`pn` greater than every number it already issued and `< 2^62`, and only
while the per-key confidentiality limit allows. Reuse, regression,
out-of-range and exhaustion are typed errors. `seal` consumes the ticket on
success. Every check (ticket origin and key generation, header form,
key-phase bit, the header's truncated pn matching the ticket, buffer and
sample bounds) runs before any byte is written; on failure the buffer is
untouched and `SealError` hands the ticket back. `abandon` burns a number
without sealing.

`NonceTicket` is non-`Clone`, non-`Copy` and `#[must_use]`, with no public
constructor. Dropping a live ticket increments `leaked_nonce_tickets()` and
leaves it `outstanding` in `Sealer::audit()`; the number is never
re-issued. These are Rust ownership and runtime checks in a host library.
They are not an implementation of the Vesper source typing rules for
`linear` values, and nothing here exercises the Vesper checker.

## Key update (RFC 9001 §6)

Generation `g` uses key-phase bit `g & 1`; the header-protection keys never
change. `OneRttKeys` tracks send and receive generations separately:

- `initiate_key_update` is allowed only when the receive side has caught up
  with the send side (the peer responded to the previous update) and a
  packet sent with the current send keys was acknowledged
  (`on_packet_acked`). It derives the next key from the "quic ku" secret;
  tickets issued under the old key become stale.
- Receive keeps the current key, the precomputed next key (so no key is
  derived during trial decryption, §6.3) and, after an update, the previous
  key. A packet whose phase bit differs from the current one goes to the
  previous key if its pn is below the first pn received in the current
  phase, and to the next key otherwise. Opening with the next key promotes
  it, and a peer-initiated update makes the send side follow (§6.2).
- The previous key is retired `retire_window_ns` after the promotion, on the
  caller's clock (§6.5 recommends three PTOs; the connection chooses).
  Packets for a retired phase fail with `KeyRetired`.
- Failed openings count toward the integrity limit across all keys; when it
  is reached nothing more is opened.

Not modelled, because they belong to the connection: requiring handshake
confirmation before the first update, and the KEY_UPDATE_ERROR policy for
consecutive updates.

## Secrets, zeroization and constant time

Where the guarantees come from:

| Property | Source |
| --- | --- |
| `TrafficSecret`, `KeyMaterial` zeroized on drop | this crate (`zeroize` derive) |
| `PacketKey` IV, ChaCha20 header key zeroized on drop | this crate (`Drop` + `zeroize`) |
| AES key schedules (AEAD and header protection) zeroized | `aes` `zeroize` feature |
| GHASH/POLYVAL state zeroized | `polyval` `zeroize` feature (feature unification) |
| ChaCha20-Poly1305 key and per-message MAC state zeroized | `chacha20poly1305`, `poly1305` `zeroize` |
| Initial PRK zeroized after expansion | this crate |
| HMAC state inside `hkdf` during expansion | **not** zeroized by `hkdf` |
| Constant-time tag comparison, before any plaintext is written | `aes-gcm` and `chacha20poly1305` (via `subtle`) |
| Retry tag verification | same AEAD path (empty plaintext) |

Tested here: a failed open leaves the payload bytes unchanged (the
dependencies verify before decrypting) and, with header protection re-applied,
the whole buffer unchanged. No constant-time claim is made beyond the
dependency guarantees: packet-number checks, key-phase selection and
packet-number length handling branch on values that header protection hides
from observers but that are not treated as secret here. RFC 9001 §9.5 timing
concerns around key updates are addressed only by precomputing the next key.

## Hardware offload

Hardware AEAD offload (kTLS, NIC inline crypto) is **not implemented and
unavailable**. No extension trait was added, since it could only be tested
against the same software implementation.

## Acceptance tests

`cargo test -p vesper-warp-crypto` (21 tests):

- `tests/rfc9001_vectors.rs`: RFC 9001 Appendix A.1 Initial secret, both
  Initial secrets and their key/iv/hp; A.2 the protected 1200-byte client
  Initial reproduced byte-for-byte by sealing pn 2, then opened by the server
  through the lane-1 boundary; A.3 the protected server Initial; A.4 the
  Retry integrity tag (plus rejection of a flipped tag, wrong ODCID and
  short packet); A.5 the ChaCha20-Poly1305 key, iv, hp, "quic ku" secret,
  nonce, mask and the 21-byte protected short-header packet, sealed through
  `OneRttKeys` and opened back. A regression test covers a ChaCha20
  header-protection sample whose counter is `2^32 - 1` (attacker-chosen,
  since header protection is removed before authentication): the buffered
  `chacha20::ChaCha20` wrapper panics on that block, so the mask is computed
  with the `ChaChaCore` block function directly and checked against a
  test-only RFC 8439 reference. The vector bytes were copied from the RFC
  source (quicwg/base-drafts `rfc9001.md`).
- `tests/protection.rs`: round trip for all three ciphers; flips in the
  first byte, header, both pn bytes, payload and tag all fail with the
  buffer byte-identical and no key state moved; wrong reconstructed pn;
  nonce reuse, regression, out of range and exhaustion; every seal failure
  returns the ticket and leaves the buffer untouched; foreign and stale
  tickets; leak counting; confidentiality limit forcing a key update;
  integrity limit; two full key updates (client-initiated then
  server-initiated) with a reordered previous-phase packet, retirement after
  the window, and update gating; offsets and sample bounds including
  `usize::MAX`; a bit flip (0x10) at every byte of an Initial packet
  rejected, leaving only that flip in the buffer; and
  deterministic garbage of every length 0–79 at every offset (no panics).
- `tests/zero_alloc.rs`: a thread-local counting global allocator (with a
  positive control) sees **zero allocations** over 1,084 warmed-up 1-RTT
  seal+open round trips per cipher, including a key update and the receive
  promotion it triggers, and over 496 Initial seal+open round trips.
  `retry_integrity_tag`/`verify_retry_integrity` allocate the pseudo-packet
  and are not on the hot path.

## Unsafe code

The library is `#![forbid(unsafe_code)]`. The only `unsafe` in the crate is
the test-only counting `GlobalAlloc` in `tests/zero_alloc.rs`, which forwards
to `System`.

## Remaining gaps

- No TLS handshake; secrets for Handshake/0-RTT/1-RTT must come from a TLS
  stack. Only QUIC v1 salts and Retry keys are included (not v2).
- AES-128-CCM is not supported.
- Handshake confirmation and KEY_UPDATE_ERROR policy live in the connection.
- Hardware offload unavailable (above).
- Wiring into lane 1's packet core is the post-wave integration step.
