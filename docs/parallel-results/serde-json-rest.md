## What was built

**1. AVX-512 stage 1 with VPCLMULQDQ quote parity** (`src/simd/kernels.rs`).
`Isa::Avx512` (AVX-512F + AVX-512BW + VPCLMULQDQ, detected at run time) loads
each 64-byte block into one `zmm` register. Byte classes come straight out as
`u64` masks (`_mm512_cmpeq_epi8_mask`, `_mm512_cmple_epu8_mask`) from the same
nibble shuffle tables; UTF-8 uses the same Keiser–Lemire tables, with the
previous bytes assembled by `_mm512_permutex2var_epi64` + `_mm512_alignr_epi8`.
Four blocks are processed per step: classification and the escape carry chain
run per block, then **one `_mm512_clmulepi64_epi128` computes the four quote
prefix-XORs** (each mask in the low quadword of its own 128-bit lane, times
all ones). `unsafe` stays confined to `kernels.rs`.

NEON (`Isa::Neon`, with PMULL) already existed; it was re-run here (below).
**SVE: no path.** Rust's SVE intrinsics are not stable, so an SVE host uses
NEON; `Isa::sve_reported()` exposes the CPU flag and the stage 1 test prints
it. Under `qemu-aarch64` (default `max` CPU) it reports `true`, and NEON ran.

`Isa::detect()` now prefers AVX2, then NEON, then SSE4.2, then AVX-512: on the
only AVX-512 host available the AVX-512 path measured slower than AVX2 (see
throughput), so it is opt-in through `parse_with_isa` / `SimdParser::with_isa`
rather than a silent regression.

**2. Eisel–Lemire float decoding** (`src/lemire.rs`, `src/pow5.rs`,
`pub mod number`). `number::decode_f64(text) -> Option<(f64, DecodePath)>`
parses the JSON number grammar (with SWAR eight-digit folding), then tries
Clinger's exact fast path (significand ≤ 2^53, |q| ≤ 22), then Eisel–Lemire
over a 651-entry 128-bit power-of-five table (q = −342..308; significands of
more than 19 digits are tried as `w` and `w + 1` and accepted only when both
round alike), and falls back to `str::parse::<f64>` when Eisel–Lemire cannot
decide. `Node::as_f64` / `Cursor::read_f64` use it; overflow to infinity is
still a `Number` error and admission limits are unchanged. The table is
generated by `tools/gen_pow5.py` and rechecked entry by entry by a test that
recomputes it with an independent bit-serial big integer.

**3. Limits.**
- *Stage 1 index memory counts in `max_index_bytes`.* `IndexPlan` splits the
  allowance: the token tape's reserved capacity first (unchanged), then 4
  bytes per stage 1 entry (each structural position and each escape-starting
  backslash). Stage 1 keeps both kinds in **one** `u32` buffer (structurals
  from the front, escapes from the back, reversed into order at the end) that
  never grows past the allowed entries or one entry per input byte. A
  document with more entries is *truncated* (`StructuralIndex::truncated_at`)
  instead of failing up front. `IndexLimits::max_structurals` became
  `max_entries`.
- *The same first error in every engine.* The scalar parser now charges the
  same entries in document order (value starts, operators, closing quotes,
  escapes and the second backslash of a surrogate pair) and fails with
  `AllocationLimit` at the first one that does not fit. Stage 2 was rewritten
  to meet errors in the scalar parser's order: it pushes a scalar's token
  before validating it, walks string units (ordinary runs, escapes, control
  bytes, closing quote) in byte order with the string limit checked per unit,
  and reports truncation exactly where the scalar count runs out. Work is
  modelled by the scalar parser's **frontier** (`max_work − len − dup`, the
  first byte whose step would exceed the budget, moved past an escape body
  when it falls inside one): every error candidate carries how far the scalar
  parser had stepped when it would see it, and becomes `WorkLimit` at the
  frontier when that comes first. `work_used` and tapes are unchanged.
- `IndexedJson::index_bytes()` = tape capacity + 4 × entries (identical in
  every engine); `NdjsonBatch` charges that against its batch
  `max_index_bytes` and reports it in `BatchStats::index_bytes`.

**SWAR key matching in `tiles`.** `tiles::SwarKey` compiles a key of up to 16
printable ASCII bytes to two little-endian `u64` words; an unescaped key
matches with a length check and two word compares, escaped spellings decode
first (`"flags"` matches `flags`). The five §20.5 keys are compiled in a
`const`.

**4. Lean.** `lean/SimdJsonQuotes.lean` (generated by
`tools/gen_lean_quotes.py`) proves, about Lean models:
- `clmul_ones_eq_shifts`: the low 64 bits of the carry-less product by all
  ones (what PCLMULQDQ, PMULL and each VPCLMULQDQ lane compute) equal the
  shift cascade `prefix_xor_shifts`; proved algebraically (shift distributes
  over xor, `x <<< 64 = 0`) plus `bv_decide` for uniqueness of the recurrence
  `p = x ^ (p << 1)`, i.e. bit 0 is `x[0]` and bit i+1 is bit i xor `x[i+1]`,
  the per-bit reference's definition.
- `in_string_recurrence`, `in_string_carry_out`: with the block carry (0 or
  all ones) the string mask satisfies `s[0] = q[0] xor c`,
  `s[i+1] = s[i] xor q[i+1]`, and the next carry (`sshiftRight 63`) is all
  ones exactly when the block ends inside a string.
- `whitespace_x86/neon`, `operator_x86/neon`, `control_x86`: for all 256
  bytes, `WS_TABLE` and `OP_TABLE` under x86 `pshufb` semantics and AArch64
  `tbl`-on-low-nibble semantics, with control bytes masked out of the
  operator class, select exactly space/tab/LF/CR, exactly `{ } [ ] : ,`, and
  exactly 0x00..=0x1f; and the table alone also matches 0x0c and 0x1a (why
  the mask is needed).

**Lean was run in this session** (`lean-4.24.0-linux.zip` from the GitHub
release, unpacked with Python): both `SimdJsonQuotes.lean` (≈2 s) and the
existing `SimdJsonEscape.lean` check with no errors or warnings in the new
file, no `sorry`/`admit`/axioms/`native_decide`. `tests/lean_models.rs` runs
the new file when `VESPER_LEAN` is set (as CI does), rejects escape hatches,
and checks that the two tables in the Lean file are the ones in
`kernels.rs` (a one-entry change to `WS_TABLE` makes it fail). These are
theorems about the Lean definitions, not about the compiled Rust; the kernels'
agreement with the scalar reference is tested.

## Measured throughput

`cargo run --release -p vesper-serde --example simd_throughput`, best of 7
timed repetitions of ≥150 ms each, rustc 1.97.0, a 4-vCPU cloud VM reporting
"Intel(R) Xeon(R) Processor @ 2.10GHz" with AVX-512F/BW/VL/VBMI and VPCLMULQDQ,
no other load. Same data as wave six: a 750 KB array of objects and a 3.4 MB,
20,000-line telemetry NDJSON file. Two runs on this branch:

| Path | Stage 1 MB/s | Full parse MB/s | NDJSON → tiles MB/s |
| --- | ---: | ---: | ---: |
| Scalar reference | 300–313 | 202–204 | 141–147 |
| SSE4.2 | 1,909–1,911 | 467–468 | 244 |
| AVX2 | 2,986–3,007 | 507–520 | 256–260 |
| AVX-512 + VPCLMULQDQ | 2,576–2,584 | 478–495 | 260–264 |

- **AVX-512 is about 14% slower than AVX2 in stage 1 on this host.** Replacing
  the four-way VPCLMULQDQ with four scalar PCLMULQDQs gave the same numbers, so
  the carry-less multiply is not the bottleneck; the shuffle-heavy
  classification and UTF-8 check do not get faster per byte with 512-bit
  registers here, and the per-block scalar work (escape chain, index writes)
  dominates. Hence `detect()` keeps AVX2. No other AVX-512 machine was
  available to compare.
- The same example on unmodified `origin/main` in the same session: AVX2 parse
  519, tiles 259, SSE4.2 parse 484 MB/s. Before a fast path for plain strings
  the rewritten stage 2 was ~10% slower; with it, parse throughput is within
  noise of `main` (507–520 vs 519).
- Float decoding, 100,000 shortest-round-trip spellings of random positive
  doubles (2.2 MB): `decode_f64` 698 MB/s (31.7 M numbers/s), `str::parse`
  747 MB/s (33.9 M/s). Rust's `core` already implements Eisel–Lemire, so this
  is the expected neighbourhood; ours additionally reports the path taken.
- No AArch64 throughput was measured (QEMU timings are meaningless).

## Decisions

- **Engine-independent limits rather than per-engine ones.** Counting stage 1
  memory only in the SIMD engine would make acceptance depend on the engine;
  instead the scalar parser counts the same entries, so `max_index_bytes`
  means the same thing everywhere and the scalar parser stays a complete
  oracle. `AllocationLimit` (an existing kind) reports it: adding an
  `ErrorKind` variant would break an exhaustive match in `vesper-lsp`, which
  this lane does not own.
- **Exact error agreement by construction of the walk order**, not by
  re-running the scalar parser on failure (which would make the error path
  allocate and turn the differential test into a tautology).
- **Truncate instead of failing in stage 1**, so a document whose syntax
  error precedes the overflowing entry still reports the syntax error, as the
  scalar parser does.
- **One buffer for structurals and escapes**, so stage 1 memory is bounded by
  the entry allowance exactly, without a separate cap per kind.
- **Keep `str::parse` as the fallback** (it is correctly rounded with its own
  big-decimal path) instead of writing a big-decimal slow path.
- **AVX2 before AVX-512 in `detect()`**, from the measurement above.

## Remaining gaps

- No SVE (or SVE2) path: Rust SVE intrinsics are unstable; SVE hosts use NEON
  and are reported. No RISC-V vector path.
- AVX-512 was measured on one VM only, where it loses to AVX2; it is
  correct (bit-identical masks) but opt-in.
- The Lean models cover the escape kernel, quote parity with the block carry
  and the classification tables; not the Keiser–Lemire UTF-8 tables, the
  structural derivation in `block_finish`, stage 2 or the float decoder. They
  are not proofs about the compiled Rust.
- Float decoding is binary64 only (no f32), and the Eisel–Lemire code is a
  transliteration of the published algorithm checked by differential tests,
  not a proof.
- `SimdParser` retains buffer capacity from earlier, larger documents, so the
  memory it *holds* can exceed the current document's `max_index_bytes`; what
  a parse may *use* never does.
- Unchanged from wave six: no `eff [Isa[P]]` typing, `@derive(JsonDecode)`,
  `tiled(16)` lowering or Region arenas; Rust ownership here is not evidence
  for Vesper source typing rules.
