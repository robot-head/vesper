# Pulse pool startup failure and cancellation coverage

Issue #573 follows the user-supplied timeout of `cancelling_the_pool_completes_parked_reads_on_every_worker` on PR #412 at `57498bfd27276a1549cf36d0f920d7f8df135651` (invocation `c5b10f48-8f04-44e1-bbec-1d76622eee7c`). The other two pool integration tests completed. That log does not identify the backend or prove whether the stall was in startup, cancellation, draining, or joining.

The unchanged actual Bazel target passed locally, followed by 200 direct executions of its complete three-test binary and 200 cancellation-only executions. The available backend is epoll; the host denies io_uring with `EPERM`. A separate controlled resource failure exposed a production startup deadlock: a limit applied only to an owned child allowed one real worker to start, then the next OS thread creation failed with `WouldBlock` / OS 11. `spawn_scoped(...).expect(...)` panicked while the created worker waited at `Barrier(3)`, and scoped unwinding waited to join that worker. After five seconds, the child still had its main/test/worker threads waiting on futexes, an unregistered epoll descriptor and the retained pipes. Its state was captured before that child alone was terminated and reaped. Parent and global process limits were unchanged. This demonstrates the partial-startup defect; it does not establish that the hosted timeout had the same cause.

`Pool::run` now uses a one-shot, abortable startup gate. Normal execution still waits for every configured driver's setup before any fiber runs. An OS thread creation error records the existing typed setup error, aborts the gate, releases and joins created workers, then returns the pool through `RunError::Setup`. Workers completing setup after the abort also leave immediately. Their published wake writers and built drivers/readers are dropped through the existing setup cleanup. Factory errors retain the intact-pool return path; factory panics still propagate after sibling cleanup. Driver cancellation and wake implementations are unchanged.

A deterministic unit regression places one real thread in a three-participant gate, confirms it has arrived without being released, aborts setup, and checks that both the waiting participant and a later arrival are released as aborted. Existing factory-panic and typed setup-error/retry tests remain. A supplemental temporary Rust harness links the actual patched Bazel production library and uses the real epoll driver. With a child-only thread limit, it observes `Setup(worker=1)` before any read or cancellation trigger runs. It restores that child's original soft limit and reruns the same returned pool, completing all seven original fiber IDs. This checks recovery through the public API; the harness is not described as a workspace Cargo or Bazel test target.

The original six-read, three-worker, 20-yield cancellation workload and all its assertions remain. Writers stay owned until each run finishes, so EOF cannot substitute for cancellation. A separate regression covers two explicit cases on every driver the host can start: pre-cancellation requires six unstarted readers and zero read starts/submissions; the submitted-read case waits for six `Read(Start)` observations and requires six typed `Cancelled(Io)` results plus exactly two submissions per worker. The counter increments before the I/O step, retaining the cancellation/post-submit handoff. It does not assert that all three workers were blocked in kernel polling. Its readiness deadline fails and cancels rather than skipping a case. Direct stderr backend/run/trigger phase messages bypass libtest capture so a process-level timeout can retain progress information.

Validation uses pinned Bazel 9.3.1 with the repository's Rust 1.100.0 toolchain, system configuration, a 2 GB JVM, one build job and shared disk cache. The initial actual unit/integration invocation passes 40 unit tests and four integration tests in 21.387 seconds. Twenty uncached repetitions of both actual targets pass all 880 reported Rust test cases in 22.476 seconds, configured with three test threads. Existing io_uring capability refusal remains visible; these counts do not claim kernel io_uring execution. Actual package `:clippy` and `:rustfmt` targets pass in a separate 19.537-second invocation with the repository's strict warnings policy. The local diagnostic command timeout is 90 seconds; no repository CI timeout or budget is increased.
